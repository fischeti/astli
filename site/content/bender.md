# Coming from Bender

[Bender](https://github.com/pulp-platform/bender) is a popular dependency management and filelist generation tool developed by the PULP Platform team.

`astli` is designed to coexist smoothly with Bender projects and provides an easy, incremental migration path. You don't have to rewrite your existing infrastructure overnight.

---

## What `astli` reads from `Bender.yml`

If your project directory contains a `Bender.yml` file, `astli` automatically reads its declared dependencies, as long as your `astli.toml` does not define its own `[dependencies]` table:

- **Git dependencies**: `git` URLs with semantic versions or explicit `rev` git revisions.
- **Path dependencies**: Local `path` references.
- **Remote shorthands**: Named remotes and package names, normalized to lowercase following Bender conventions.

!!! info "What `astli` ignores in `Bender.yml`"
    `astli` intentionally does **not** read Bender's `sources`, `defines`, or `targets`:
    
    - Source files are discovered automatically via standard directory scanning (see [Packages](packages.md)).
    - Conditional compilation targets are represented using [Features](features.md).
    - `Bender.lock` is ignored. `astli` maintains its own deterministic lockfile in [`astli.lock`](dependencies.md#lockfiles-astlilock).

## Step-by-step migration

You can migrate a Bender project to `astli` in four gradual steps:

### Step 1: Use `astli` on Bender's filelist

Without modifying any repository files, you can immediately use `astli` to check, lint, or trim filelists generated by Bender:

```sh
# Generate a complete filelist using Bender
bender script flist-plus -t rtl > design.f

# Check and verify the design with astli
astli check -f design.f --top soc_top
```

### Step 2: Add an `astli.toml` for formatting and linting

Run `astli init` in your repository root. It writes a minimal `astli.toml` with the package name inferred directly from `Bender.yml`. You can then configure formatting preferences, linter waivers, or custom source search directories:

```toml
[package]
name = "my_soc"

[fmt]
width = 100
indent = 2
```

Because your `astli.toml` omits `[dependencies]`, `astli` continues to read your dependencies transparently from `Bender.yml`. You can now run `astli fmt`, `astli lint`, and `astli check` directly across your repository without generating intermediate `.f` filelists.

### Step 3: Transition dependencies to `astli.toml`

When you are ready to manage dependencies natively with `astli`, run `astli bender import` (or manually copy your dependencies). This copies Bender's dependency definitions into `[dependencies]` in `astli.toml`, creating the file if there is none:

```toml
[dependencies]
common_cells = { git = "https://github.com/pulp-platform/common_cells.git", version = "1.38" }
axi = { git = "https://github.com/pulp-platform/axi.git", version = "0.39" }
```

Once `[dependencies]` is defined in `astli.toml`, `astli` exclusively uses its own native resolver and lockfile.

!!! note "Target-specific dependencies"
    `astli bender import` omits dependencies that are restricted to specific Bender `target`s (such as simulation testbenches or FPGA builds). In `astli`, flow-specific dependencies and conditional compilation are managed declaratively using [Features](features.md).

### Step 4: Let `astli` write `Bender.yml`

If others still build your package with Bender, keep `astli.toml` as the one file you edit and generate `Bender.yml` from it:

```sh
astli bender export
```

Commit the result, since Bender reads a dependency's `Bender.yml` at the tag it fetches. In CI, check that it is up to date; the check fails when `astli.toml` or the files changed without it:

```sh
astli bender export --check
```

The export maps `astli`'s package model onto Bender's:

| `astli.toml` | `Bender.yml` |
| :--- | :--- |
| `[dependencies]` | `dependencies` |
| a dependency only features bring in | a dependency with `target: <features>` |
| `[dev-dependencies]` | a dependency with `target: <package>_dev` |
| a dependency's `features`, and `dep/feature` in a feature | `pass_targets` |
| `include-dirs`, and a feature's | `export_include_dirs`, a feature's under its target |
| the package's files | `sources`, in dependency order |
| a feature's files | a source group with `target: <feature>` |
| `dev` files | a source group with `target: <package>_dev` |
| a `default` feature's files | sources without a target |
| a file that `[overrides]` lets replace a dependency's | a source group with `override_files: true` |

`dev` gets the package's name because a target set on Bender's command line is set in every package: `-t soc_dev` builds `soc`'s testbenches and no dependency's. Bender has no default features, so a default feature's files are always built.

Bender compiles source groups in order, so a group can appear more than once where a file needs one that a later group holds. A feature's include directory is exported under its target, which needs Bender 0.30 or later.

`astli` refuses to write what Bender would build differently: `default-features = false` on a dependency that has defaults, and a replacement Bender would apply differently. Bender puts a replacement in place of every file of the same name, in any package, and compiles it there with that package's include directories, so a replacement must have the name of the file it replaces, no other kept file may have that name, and it may not include the root package's own headers. `Bender.lock` is not written, since the package itself is built with `astli`.

!!! tip "Give each target a directory"
    Bender sorts files into targets by naming each one, so many Bender projects keep every source in a single directory. `astli` selects the sources of a feature, of `dev`, and of `exclude` by glob pattern instead, which works best when the layout already separates them. Moving each target's files into a directory of its own, such as `rtl/fpga/`, `rtl/asic/` and `tb/`, turns a long list of file names into one pattern, and a file added there later lands in the right feature without touching `astli.toml`.

## Handling version conflicts (`[resolve] pinned`)

When dependency version requirements conflict, Bender interactively prompts the user in the terminal to pick a version (or requires a local override file such as `Bender.local`).

`astli` is strictly non-interactive and scriptable: it never halts to prompt for manual user input during dependency resolution. If two packages request incompatible versions, `astli` stops with an explicit conflict error by default.

To resolve a conflict without modifying transitive upstream manifests, pin the package in `[resolve] pinned` in your `astli.toml`:

```toml
[resolve]
pinned = ["common_cells"]
```

When a package is pinned:

- `astli` forces the dependency to whichever version or revision the root package specifies.
- Any conflicting downstream requirements that cannot be met are downgraded to informative warnings rather than fatal errors.

!!! note "Projects with only a `Bender.yml`"
    A project that relies solely on `Bender.yml` has no mechanism to declare pins. If your design encounters version conflicts across its dependencies, you will need to add an `astli.toml` and declare `[resolve] pinned` to explicitly resolve them.
