# Packages

> **Status:** discovery, selection and path dependencies, phases 1 to 3,
> are built (M10, [`plan.md`](plan.md#5-milestones)), and of phase 4 the
> store (P20–P22), where each dependency comes from (P23), resolution (P24,
> P25, P27), the lockfile (P26), patches (P28), descriptions of a
> dependency without a manifest (P31), and `add` and `remove` (P33).
> Generators are designed.

`astli` should find a design by itself, without a filelist or `+incdir+`, and
in time resolve dependencies the way Cargo does. A package is a directory with
an `astli.toml`; it says what its files are, what a dependent sees of them,
and what it may replace in its dependencies. It never lists files.

## The manifest

```toml
[package]
name = "my_soc"
sources = ["hw"]                 # where the walk looks; default ["."]
include-dirs = ["hw/include"]    # header roots a dependent searches; default ["include"]
exclude = ["hw/scripts/**"]      # on top of .gitignore
dev = ["hw/tb/**"]               # never seen by a dependent

[dependencies]
common_cells = { git = "https://github.com/pulp-platform/common_cells.git", version = "1.38", features = ["asic"] }
idma = { git = "https://github.com/pulp-platform/iDMA.git", rev = "main" }   # a branch, a tag or a commit
tech_cells_gf22 = { path = "../tech_cells_gf22" }

[dev-dependencies]
axi = { path = "../axi", features = ["vip"] }

[features]
default = ["vip"]                # what a dependent gets without asking
vip  = { sources = ["hw/vip/**"], include-dirs = ["hw/vip/include"], dependencies = ["common_verification"] }
asic = { sources = ["hw/tech/asic/**"], dependencies = ["tech_cells_gf22"] }

[overrides]                      # names this package may replace in a dependency; `*` any run
tech_cells_generic = ["tc_sram", "tc_clk_*"]

[resolve]
pinned = ["axi"]                 # the root's requirement of each is the only one

[fmt]                            # as now
[lint]                           # as now
```

Every path is relative to the file. Without `[package]`, discovery uses the
defaults; `name` is needed once something depends on the package.

## What a file is

| Class | A dependent sees it | Selected by | Corpus example |
| --- | --- | --- | --- |
| Design | always | `sources`, less `exclude`, `dev` and feature sources | `axi_xbar.sv` |
| Verification IP | when it enables the feature | a feature's `sources` | `axi_test.sv` |
| Testbench | never | `dev` | `tb_axi_xbar.sv` |
| Header | through `include-dirs` | being included | `axi/typedef.svh` |

## Decisions

| # | Decision | Why |
| --- | --- | --- |
| P1 | The package root is the directory holding `astli.toml`, found walking up from the current directory as far as the git root; without one, the git root. Files or `-f` on the command line turn discovery off | A dependency in a shared store has no `.git`. A manifest above the repository is not its own. One base for every path in the file. |
| P2 | `sources` narrows the walk and stays inside the root; the root itself does not move | Covers a `hw/` beside `sw/`. The root is what a package publishes, so `sources` cannot reach outside it. Not called `include`, which SystemVerilog uses for headers. |
| P3 | The walk yields `.sv`, `.svh`, `.v` and `.vh` files, honours the `.gitignore` files at or below the root, with or without a repository, and stops at a nested `astli.toml`, at a package it depends on by `path`, and at a patched directory (P28) | Walking is cheap (80 ms over OpenTitan's 13.7k files, the same files `git ls-files` names); parsing is the cost. A dependency then reads the same from a shared store, and a package checked out where another repository ignores it is still walked. A global ignore file and `.git/info/exclude` differ between machines. A nested manifest is another package, such as vendored IP, which would otherwise clash with the dependency it copies, and a `path` dependency is one too, manifest or not. |
| P4 | A header is any file another includes, whatever its extension and in whichever branch; a unit is a file with a unit extension (`.sv`, `.v`) that nothing includes | `ibex`, `cva6` and OpenTitan include `.sv` files, 3,000 times in the corpus. A file included only where a build defines a macro is still not meant to be compiled alone. |
| P5 | `` `include `` resolves beside the including file, then in `include-dirs`, then within the package by unique path suffix; two candidates are an error where the expansion reaches the directive, and each is a header. A dependent searches only `include-dirs`, so an exported file whose include resolves only by suffix is an error. `include-dirs` defaults to `include` where it exists | No configuration inside a package; a header added to a dependency cannot make a downstream include ambiguous. Most IP already exports `include`, so one without a manifest still exports its headers. |
| P6 | Discovery finds no order and needs none. `astli files` orders what it discovers by `Index::ordered`; a filelist keeps its order unless `--order` asks otherwise | Each file is its own unit ([D17](plan.md#4-decisions)). A defines file that must come first gets an explicit define instead. A discovered package's order is only its paths', which a tool compiling in one pass cannot use, while a filelist's can carry what astli cannot see. |
| P7 | A referenced name two selected files declare is an error; an unreferenced one is a warning | Repositories hold several `tb_top`s nothing instantiates. |
| P8 | `lint` and `check` load the dependencies and report on the root package only; `fmt` formats every file the root holds, dev and feature sources included. With `--top`, `check` reports only the root's files the tops reach, and so do `lint`'s design rules, while its tree rules read every file; `check` and `files` report a name declared twice (P7) in any file the tops reach, a dependency's too. `files` fails, and writes no list, if a root file has errors, as `check` does | `check` needs the dependencies' definitions, and `lint`'s design rules their port directions; a dependency's findings are its authors' to fix, as with clippy. A file no top reaches is another top's to check, so a CI job per bench owns its bench alone. A region that did not parse may hold an instance, so a list written past it could be short and a CI job gating on `files` would pass. Which of two declarations a top's build means is the root's problem whoever's files hold them, and the filelist `files` writes for the tops and the check of them must agree. A design rule would judge a file no top builds at its defaults, but a tree rule reads a file as written, the same whatever builds it, and once a table makes the root's runs build from a top, no run would read the rest. |
| P9 | Features are additive: one adds sources, include directories and dependencies, and enables a dependency's features (`axi/vip`), never removes any. A dependency a feature names alone (`tech`) is optional, in the design only while a feature naming it is enabled. A file a feature names is walked only when a feature naming it is enabled. A package's own runs enable all its features; `--no-features` turns them off and `--features` names more of its own; a dependency's is enabled through one of them. A dependent gets `default` and what it asks for; `features` adds to the defaults, and they are off only where every requirement says `default-features = false` | Any combination is then a valid design, so all of them together is too, and that is the run that reads every file. Negation (`not(synthesis)`) is what made bender's targets hard to read. A feature's own include directory keeps it out of what every dependent searches. Every selection a run can make is then declared in the root and resolved (P27), and the root says which variants of its dependencies it supports. `default` decides only what a dependent gets, which is all a default buys when nothing conflicts. Naming a feature only adds, so that it cannot take away what another dependent relies on, and turning the defaults off is said outright. |
| P10 | A variant is an override. `[overrides]` names what a package may replace in a dependency; a replacement takes effect when a selected file of the package declares the name. Two packages declaring one name without an override, or overriding the same one, is an error | An override follows the feature that selects its file, with no condition of its own. Dependencies stay read-only. Covers generic and technology cells and regenerated register files alike. |
| P11 | A file is kept or dropped whole, so a dependency file declaring both a replaced and a kept name is an error | As in file selection ([M6](plan.md#m6-astli-files-and-astli-pickle)); splitting a file is a rewrite. |
| P12 | Tool support is not modelled: `` `ifdef VERILATOR ``. No cfg attributes, and a package exports no defines; only the root's tops set any (P32) | Every tool predefines its macro. A tool has to parse a file to ignore an attribute in it, so an attribute selects only where astli writes the file list or the pickle, and within a file `` `ifdef `` already works in every tool. A file list can only define a macro for every file, so a define is the consumer's. |
| P13 | Generators come last: declared by the package whose files they write, parameters from the dependent, output in the dependent's `target/`, cached by inputs and parameters. The output replaces the package's checked-in default without an override, and a missing output is reported | A `build.rs` without the code: dependencies stay read-only and shareable between projects. Until then, regenerating into the root package and overriding does the same by hand. |
| P14 | No `bender` process runs. Of a `Bender.yml`, only its dependencies are read (P23); targets, file lists and defines are not | astli fetches and resolves itself (P20, P24), and none of bender's file model reaches astli: what an IP exports and leaves out is its `astli.toml`'s to say. |
| P15 | Selection is per design: features, overrides and each dependency's version are settled once. Two dependents asking for different features of a package get both; asking for different versions, or overriding one name, is an error naming both. No feature excludes another | Every name is global to the design, so a dependency cannot be two ways at once. What varies per instance is a parameter; a configuration package such as `cva6`'s cannot. Until names are mangled, a second copy is `astli pickle --prefix`. |
| P16 | A private package depends on the public one it builds on, by `path = ".."` when checked out inside it. A dependent never resolves a package's dev-dependencies, so what the private side reuses, such as synthesis wrappers or a simulation fixture, is a feature, not `dev` | A public manifest then names nothing its users cannot fetch, and the path follows the surrounding checkout, so neither repository updates a link when the other changes. The other direction needed a stub manifest for the private package. |
| P17 | A dependency is a package, read as a root is: its manifest or the defaults, its walk, its headers and units, its own build. A package searches its own `include-dirs`, then those of every package it depends on, directly or not. Where a dependency's directory comes from is the resolver's (P24), and the packages search each other's headers in bender's order: the farthest from the root first, ties by name | One model whatever fetched it, so dropping bender changed only where the directories come from, and its order keeps a header two dependencies ship resolving as it did. Searching what a dependency's dependencies export spares listing a package only for its headers. |
| P18 | `dev` patterns match as `exclude`'s do. A dependent's walk of the package skips them, so a dev file is neither compiled nor found by an include, while the package's own runs read it as any other | Otherwise each design built on a package compiles its testbenches too: common_cells' 28 under `test/` in every design with axi. A header only a testbench includes is not the dependent's to find. |
| P19 | An override replaces a unit, never a header. What a header declares is replaced through the unit that includes it | A dependency searches its own include directories first and never its dependents', so nothing a dependent ships can shadow its headers, and `[overrides]` holds names, not paths. |
| P20 | astli fetches a dependency's repository itself, with `gix`, into a cache every design on the machine shares: `ASTLI_CACHE_DIR`, or `astli` in `XDG_CACHE_HOME` or `~/.cache`. It holds one bare mirror per repository, keyed by its URL as compared: host and path in lower case, without scheme, user or `.git`, so that HTTPS and SSH name one mirror; holding every branch and tag; and one checkout per commit, written once, without `.git`; `astli fetch` resolves as any run does and checks every package out ahead of time, so that later runs need no network. A run checks out only what it reads, and `astli path NAME` prints where one is. A checkout's files are read-only and its directories writable, and a list of what the commit holds is kept beside it: a walk refuses any other file in it. `astli cache dir` prints where the store is, and `astli cache clean` deletes it, waiting for each mirror's lock | No `bender` process. A cache is what can be deleted and fetched again, so it goes where uv keeps its own. A fork is another URL, so another mirror. Resolution reads versions and manifests from the mirror, and only what a design uses is checked out, read by every design that uses it. A file put into a checkout by hand, as bender's users put generated files into `.bender/`, would change the package for every design, so it is refused where it would be read, with what to do instead: generate into the package that needs it and override (P13). Deleting the store stays plain, which read-only directories would prevent; `cache clean` also takes the locks, and clears Windows' read-only flag, which `del` refuses. The command is `cache clean`, as uv's, since `clean` will be for a dependent's generated `target/` (P13). `path` is for what the package model has no word for, such as a register description; source files are `astli files`'. |
| P21 | A version is a tag `vX.Y.Z`, read as semver. A `rev` is a branch, a tag or a commit, as git reads it. A commit no branch or tag reaches is fetched only when a `rev` names it by its full id | bender reads tags the same way, and the corpus tags so. Fetching everything nothing references rewards tracking a branch that is then force-pushed, but FlooNoC and iDMA pin `axi` to such a commit, which a forge still serves by its id. |
| P22 | A submodule is not checked out: it is an empty directory. Line endings are the repository's, whatever the machine's `core.autocrlf` or `core.eol`, and no filter program runs | A dependency is the files its own repository holds, and one checkout serves every design and must read the same on every machine. Submodules pull in software trees, and what a design needs from one is a dependency of its own. cva6's checkout then lacks its `riscv-dbg` and `cvfpu`, which bender's has. |
| P23 | A package's `[dependencies]` table, when its `astli.toml` has one, is its whole list; without the table, the `dependencies` of its `Bender.yml`, names lowercased as bender does. An entry is `git` with a `version` requirement or a `rev`, a `path`, or in a `Bender.yml` a bare version of what a remote names. A `Bender.yml` dependency with a `target` is left out, and its other keys are ignored | One requirement whichever manifest wrote it, read from text so that resolution reads it at any commit. A bender project adding an `astli.toml` for `[fmt]` keeps its dependencies. Most IP has only a `Bender.yml`, and reading it is what keeps a real design's graph whole. astli has no targets (P12), so what only some builds want is not the design's. |
| P24 | Resolution is PubGrub's, over commits: a version requirement admits the commits a matching `vX.Y.Z` tag is on, a `rev` its commit, so a commit without a tag meets only a `rev` naming it. The highest version admitted is chosen. Requirements are strict; a package the root names in `[resolve] pinned` takes the root's requirement alone, and each other requirement of it the choice does not meet is a warning | Strict, since a conflict hidden is a design built against a version a dependency never meant. bender lets the root's requirement decide: cheshire resolves only by replacing five of its dependencies' requirements, each of a package the root lists. Pinning says so in the manifest, where bender asked at the terminal, and the warnings keep it from passing unseen. A root with only a `Bender.yml` has no pins, so a design that resolves only by letting the root decide, as iDMA, FlooNoC and cheshire do, needs an `astli.toml` to name them. |
| P25 | A package has one source in a design: every requirement of it names the same repository, URLs compared as P20 does, or the same directory, unless the root pins it. A `path` in a repository's manifest is a directory of that repository at the same commit, never outside it; a `path` on disk is that directory | A fork is another package, and names are global, so one design holds one of them; snitch_cluster takes `axi` from a fork its root names, so that is what a pin settles. A path inside a fetched repository has nothing beside it to point at, and the commit that holds it pins it. |
| P26 | `astli.lock`, beside the root's manifest, holds the commit chosen for each package from a repository, and the `rev`s that named it. A resolution chooses the locked commit while every requirement admits it, and a `rev` keeps its locked commit while the lock names it by that `rev`. A repository whose locked commits are all in its mirror is not fetched; if the lock no longer holds, resolution runs again with every mirror fetched. Every command that reads the dependencies resolves over the lock, and writes it when it changed and the root has an `astli.toml`; `--locked` fails instead. `astli update` resolves again and writes the lock in any package, and `astli update NAME` sets aside only those packages. `astli tree` prints what the resolution chose, each package under those that need it; one needed in more than one place lists its own dependencies where it first appears and is marked `(*)` elsewhere. Only the root's lock counts, and a format other than this astli's is refused | Cargo's lock: the design stays as built until someone asks for it to move, and a run with a lock that holds needs no network. A branch moves upstream, so its commit is locked by name, and naming another branch moves it. A package on disk, or a directory of another package's repository, follows from the manifests, and features are computed, so neither is locked. Without migration paths, an older format is written again rather than read. `Bender.lock` is never read: what bender chose is the bender build's. A project only bender manages gets no file it did not ask for; CI gets `--locked`, as with Cargo. A tree that repeated what a shared package needs at every path to it would grow with the paths, not the packages, so it is listed once, as `cargo tree` does. |
| P27 | A feature is resolved as a package of its own at the same versions, which depends on its package at exactly its own version and on what it brings in; `default` stands for the default features. The root's features are all on, and its `[dev-dependencies]` resolve with its `[dependencies]`. A version that lacks a feature asked of it is passed over | As uv resolves extras, and with the outcome Cargo has: one lock whatever `--features` a run selects, holding only what some selection can use, since an optional dependency nothing enables is neither fetched nor able to fail the resolution. A dependency's dev-dependencies are its own (P16). |
| P28 | A dependency is worked on in place by patching it: `astli patch NAME DIR`, or `clone`, points `NAME` at a directory, cloning its repository there at the locked commit when the directory does not exist, and into `.astli/patch/NAME` without `DIR`. Patches live in `.astli/patch.toml` in the root, beside a `.gitignore` of `*` astli writes, and only the root's count. A patched package is read from its directory as a `path` dependency is and meets every requirement of it; each run notes that it is used, and one the design does not use is a warning. While a patch is in place the lock is read and never written, and `--locked` and `astli update` fail. `astli patch --remove NAME` drops the patch and leaves the directory. `astli snapshot NAME` writes the commit the directory has checked out into the root's `astli.toml` as a `rev`, pinning `NAME` when another package requires it too, drops the patch and locks the commit. It refuses uncommitted changes, a commit no branch or tag of the repository reaches, and a root whose dependencies come from a `Bender.yml` | Editing a dependency where the design uses it, without its published manifest changing. A directory is one machine's, so a patch is never committed: a `.gitignore` in astli's own directory keeps it so, where a rule in the project's, as `Bender.local` relied on, gets lost or never written. A directory has no tag to meet a requirement with, so it meets them all, noted as a pin's overruled requirements are (P24). A lock written while patched would change again once the patch is gone, and CI never builds against one. A commit made in the clone has no tag, so only a `rev` admits it (P24), and the root's manifest then says the design builds on it; one only the clone holds, nobody else can fetch. A `Bender.yml` is the bender build's to edit. The cache cannot be worked in: its checkouts have no `.git`, and are shared and sealed (P20). The clone is the person's to commit in and push from, so their own `git` makes and reads it, with their configuration; the store stays `gix`'s alone. |
| P29 | astli writes no script for a tool. `astli files` writes the file list every simulator and synthesis tool reads with `-f`, its include directories as `+incdir+`, and with `--emit` each part alone; what a tool is run with besides is the flow's | A script holds a tool's options, libraries and elaboration steps, which differ between flows on one tool and change with its versions, so astli would keep one generator per tool and still not write the script a flow needs. bender's scripts are each such a generator. A file list is the one input every tool takes, and a flow that wraps it in its own script keeps what is its own in one place. |
| P30 | `astli init` writes an `astli.toml` in the current directory with `[package] name` alone: the `Bender.yml`'s package name, lowercased, or else the directory's. `astli bender import` copies the `Bender.yml`'s dependencies as P23 reads them into `[dependencies]`, a lone caret requirement written as the bare version bender wrote, into the `astli.toml` there or a new one `init` would write; one that already has the table is refused. An existing `astli.toml` is never overwritten by `init`. There is no `astli new` | astli reads a package with no manifest (P1, P17), so a manifest is needed for the name a dependent calls it by, and for what has no default; empty tables would say nothing. The table replaces the `Bender.yml`'s list (P23), so copying is a step taken on purpose, not a default, and the step after it is P34, which keeps the `Bender.yml` from drifting. A `Bender.yml` is the bender build's to edit until then, which is also why `astli snapshot` needs the table (P28). A project usually has an `astli.toml` for `[fmt]` before it moves its dependencies, so importing adds to it. A hardware repository rarely starts from a template, and `git init` plus `init` is what `new` would be. |
| P31 | The root may describe a dependency that has no `astli.toml`: `[described.NAME]` holds the `sources`, `include-dirs` and `exclude` its manifest would, relative to the dependency's root, and the dependency is read as if its manifest said so. Nothing else of a manifest can be described, and resolution and the lock never read it. Only the root's descriptions count. Once the dependency has its own `astli.toml`, at the commit chosen or where a patch points, that manifest is read and the description is not, with a warning to remove it. `astli files` and `astli tree` name the described ones in a note, unless `-q`, and `astli tree` marks them `(described)`; `check` and `lint` do not, since there it would read as a finding about the design. A description of a package the design does not hold, and an `exclude` pattern that matches none of a checkout's files, are warnings; an include directory or source that does not exist is an error, as in a manifest | Most dependencies have no `astli.toml` yet, and with the defaults a walk takes all of one: `tech_cells_generic` declares its cells for the FPGA and as RTL alike, and iDMA exports none of its headers. `[overrides]` replaces names, but cannot drop files or export directories. A description is a stopgap for a manifest upstream, so it says only what a manifest's file selection would, written so that it moves there unchanged; choosing versions stays with the dependency's own requirements. Upstream always wins, so that a description cannot outlive the reason for it, and the note keeps it in sight wherever dependencies are the subject. A library's descriptions would make its dependents depend on them, so each design describes for itself, and the repetition is the case for fixing it upstream. A description is committed and the same on every machine, unlike a patch (P28), so `--locked` allows it. |
| P32 | The root may say what a top needs: `[top.NAME]` holds the module it builds, `top`, the table's name by default, and its `defines`. `--top NAME` takes the table of that name, or else the module; a table named as a module other than the one it builds is an error. Without `--top`, a run builds from `[package] default-top`, else from the only table; with several tables and no default it is an error, and with none it builds every file at its defaults. The defines of tops built together are joined, and one macro defined two ways is an error; a flag's define comes after them, and wins. `check`, `lint` and `files` read the tables, and `files` writes their defines as `+define+`. Only the root's count | A design that means nothing without a define otherwise needs a wrapper to repeat it, and `--top`, on every call. Selected by `--top`, a table needs no flag of its own, and one named as its module changes nothing for a run that already names it; named as another module, which of the two `--top` means is a guess. A dependency's tops are its own CI's, so a dependent inherits no define and P12 holds. A run without a top judges every file at its defaults, which a root's modules rarely build at, so a single table is what the root is built from; a second fails loudly rather than changing what a CI job checks, as `cargo run` does once a package has a second binary. A file list defines a macro for every file, so tops built together share their defines, and the list `files` writes and the check of the same tops must agree. `elab` and `pickle` read only files named, so they have no tables to read. No flag runs every table: each defines its own macros, so each is a build of its own, and a CI job per top says which one failed |
| P33 | `astli add` and `astli remove` change the root's `astli.toml` and resolve over the lock, as any run does, putting the manifest back if that fails. `add URL` names the package as the manifest at the commit it requires does, `[package] name` or else the `Bender.yml`'s, and else after the URL's last part; it requires the highest `vX.Y.Z` tag that is no pre-release, written in full as a caret requirement, and a repository without one is refused unless `--rev` says what to track. `add --path DIR` requires a directory by its path from the manifest, named as its manifest names it or after the directory. `add NAME` requires a package the design already holds from where it comes, at the version it is locked at, or by the `rev` or commit that names it without one; one only another repository's `path` reaches is refused. An entry already there is changed in place: a new source replaces every source key, `--version` or `--rev` alone only which commit, `--features` adds to its features, and the rest stays. `remove NAME` drops the entry, and every mention of it in the root's features and `[resolve] pinned`. Both write `[dev-dependencies]` with `--dev`, and refuse a root whose dependencies come from its `Bender.yml` | Editing the manifest and then running some command to move the lock is two steps where a typo in the first shows only in the second; doing both at once never leaves a manifest the design does not resolve with. A dependent needs the name the package calls itself by, which only its manifest knows, and the highest release is what one starts on; written in full, it says which release the root was first checked against, and still admits every later one of its series. Without a tag there is no series to admit, and silently tracking a branch would be a choice the reader never made. A package already in the design is most often what one comes to require directly, and the lock already says where it is and at what version. Changing an entry in place keeps what the person wrote and astli has no opinion on. A feature or pin naming a dependency the root no longer requires would fail the next run. A description, an override and a patch name a package rather than a requirement, and another dependency may still bring it in, so they stay; a description or patch the design no longer uses is already a warning. Adding a `[dependencies]` table would replace the `Bender.yml`'s list (P23), which is the bender build's to edit |
| P34 | `astli bender export` writes the root's `Bender.yml` from its `astli.toml`, marked as written so, and `--check` writes nothing and fails if the file is not what it would write. A root whose dependencies its `Bender.yml` lists is refused. Each requirement is a dependency with its source; one only features bring in has `target: any(<features>)`, a dev-dependency `target: <name>_dev`, and the features it enables there are `pass_targets`, under the target of the feature enabling one. `include-dirs` are `export_include_dirs`, a feature's under its target. The root's units, ordered as `astli files` orders them with every feature on, are grouped by what builds them: always, a feature's `target`, `dev`'s `<name>_dev`, and a file replacing a dependency's in a group with `override_files`; each joins the first such group no earlier than one holding a file it uses, and starts a new one if there is none. A `default` feature has no target. An override group has no include directories. Refused: `default-features = false` on a dependency with defaults; a replacement named otherwise than the file it replaces, named as a file of another package the design keeps, or including a header of the root; and a feature or `dev` whose name is no bender target. `Bender.lock` is not written | bender's users fetch the `Bender.yml` at a tag, so it is committed, and `--check` in CI catches an `astli.toml` changed without it, which a list of files would otherwise miss for every file added. The project itself is built with astli, so its lock is `astli.lock`. A bender target is a condition a dependent sets or passes down, which is what a feature is, so each feature is its target. `pass_targets` sets one for that dependency alone, as a feature of a dependency is, and a dependency's `target` keeps it out of the build without one. An include directory under a target needs bender 0.30, and only a feature's has one. A target named on bender's command line is set in every package, so `dev`, which only the package's own runs read, is named after the package, where `test` would turn on every dependency's testbenches. bender has no defaults: what a dependent gets without asking is what bender builds always, and what it cannot turn off is refused rather than built. bender replaces a file by name where astli replaces what it declares, so a replacement under another name would leave both in the build; it replaces every file of that name, in whichever package; and it compiles the replacement where the original was, with that package's include directories, ignoring the group's. Bender compiles the groups in order, so a file goes after every group holding what it uses, and into a group already there where it can, so that the order holds with as few groups as it allows. |

A variant is never a feature, since all features together must be a design.
cva6 ships 19 configurations, each a file declaring `cva6_config_pkg`, so
enabling them all would declare it 19 times. Instead cva6 keeps one default,
and each other configuration is a package nested in it, such as
`core/include/configs/cv64a6_imafdc_sv39/astli.toml`, depending on cva6 by
`path` and overriding `cva6_config_pkg`. cva6's walk stops at the nested
manifests (P3), so its own runs read the default; `check` inside a
configuration checks cva6 under it; and a design picks one by depending on
it. Without path dependencies, cva6 excludes all but one, and a dependent
wanting another copies it and overrides.

Large monorepositories are not a target: OpenTitan declares 209 names more
than once under `hw/`, one per top, which only separate packages can tell
apart.

## Phases

1. **Discovery (M10).** P1–P8 without features: `fmt`, `lint`, `check` and
   `files` run with no arguments. Dependencies, each read as a package
   (P17), were located through bender until phase 4, and reporting is the
   root package's.
2. **Selection.** `dev`, features, overrides.
3. **Path dependencies.** `[dependencies]` and `[dev-dependencies]` with
   `path`, a second way to locate what P17 reads, and a feature's
   dependency named alone, which only that feature brings into the design.
4. **Package manager.** Versions, git sources, a lockfile, a shared store,
   patches, generators.
