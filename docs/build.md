# Build and run

> **Status:** `build`, `run`, `test` and `clean` with Verilator are built
> (B1, B4–B19); a simulator that compiles packages into libraries is
> designed (B2, B3). Milestone M17 in [`plan.md`](plan.md#5-milestones).

`astli build` compiles a top of the design with a simulator, and `astli run`
builds it and runs the simulation, as `cargo build` and `cargo run` drive
`rustc`. astli simulates nothing itself: it hands the simulator the files,
include directories and defines it already selects for `files`
([`packages.md`](packages.md)), with flags from a profile, and skips what an
earlier build left current. Verilator comes first; the steps below are
shaped so that Questa, VCS, Xcelium and xsim fit them too.

```toml
[build]
simulator = "verilator"          # the default; `--sim` overrides it

[top.tb_xbar]                    # as for `check` and `files` (P32)
defines = { NUM_MASTERS = 4 }
params = { NumSlaves = 2 }

[profile.dev]                    # what a run builds without `--release`
trace = true

[profile.release]
threads = 8

[profile.release.verilator]
args = ["--x-initial", "fast"]   # after every flag astli passes
```

```text
astli build                      # the default top, dev profile
astli run --top tb_xbar --release -- +SEED=3
astli run --trace                # waveforms, for this build alone
astli test                       # build and run every test the package marks
astli clean                      # deletes .astli/build, the workspace root's in a workspace
```

## The steps

| Step | Per | Verilator | Questa, VCS, Xcelium, xsim |
| --- | --- | --- | --- |
| Analyse | package | nothing | each package's units compiled into a library of its own |
| Elaborate | top and profile | the whole design verilated and compiled | the top elaborated against the libraries |
| Run | invocation | the executable | the simulator on the elaborated design |

## Decisions

| # | Decision | Why |
| --- | --- | --- |
| B1 | `build` and `run` drive a simulator astli does not ship; each is a backend behind the steps above. The root's `[build] simulator`, a workspace root's in a workspace, chooses one, `verilator` by default, and `--sim` overrides it. Verilator is the first backend, and another comes once it can be run where it is developed | A file list was the one input every tool takes ([P29](packages.md#decisions)), but what a flow passes besides it is mostly the same few flags, and only a build astli drives can tell what is current and keep what it compiled. Verilator is the open simulator, so CI can test it; a commercial one needs a licence to test against. |
| B2 | A build has three steps: analysing a package, elaborating a top under a profile, and running it. A backend without separate compilation does all its work in the second | Questa, VCS, Xcelium and xsim compile source into libraries and resolve parameters only when they elaborate, so a library compiled once serves every top that uses it. Verilator specialises each instance's parameters as it verilates, as C++ instantiates a template, so no part of a dependency can be compiled ahead of the design. |
| B3 | A package fetched into the store (P20) is analysed into the store, beside its checkout, keyed by its commit, the files the design selects of it and their contents, the defines, the simulator and its version, the profile's flags, and the keys of the packages it imports. The root and a `path` dependency are analysed into `.astli/build`, a workspace root's in a workspace, where its members share them | Cargo's metadata hash: one compiled `common_cells` serves every design on the machine that selects the same files of it with the same defines. A package exports no defines (P12) and few tops define what a dependency reads, so most designs share. An override drops a unit (P10), which changes the files and so the key. A library records the packages it imports, and goes stale when one is compiled again. A store checkout is sealed and its path fixed, so a library recording source paths stays valid; the root and a `path` dependency are edited in place. |
| B4 | A top is elaborated into `.astli/build/<simulator>/<profile>/<package>/<top>/`, beside the root's manifest or a workspace root's, where `<package>` is the package's name, or its directory's without one: the file list astli wrote, the simulator's output, a fingerprint of everything that went in, and the executable. The fingerprint hashes astli's and the simulator's versions, the simulator's arguments but for how many jobs build, the file list, and the bytes of every file and header in it, and is written once the build succeeds. `--trace` changes the arguments, so a traced build is fingerprinted apart from an untraced one in the same directory, and switching rebuilds. A build whose fingerprint is unchanged, with its executable there, runs nothing, and says it is `Fresh`; otherwise the simulator runs, and for Verilator its generated Makefile, with `ccache` as `OBJCACHE` when it is installed and nothing else is set, recompiles only the C++ that changed. A build starts once the clock is past the second the newest file in its directory was written in, which waits less than a second, and only for a build right after the last. `astli clean` deletes `.astli/build`, a workspace's from any member, and leaves the patches beside it | cheshire, iDMA and snitch_cluster commit a `target/` holding their testbenches, so Cargo's directory would mix build output with sources. `.astli/` already holds patches behind a `.gitignore` of `*` (P28), so the walk skips the build (P3) and nothing is committed by mistake. A directory per profile keeps switching from rebuilding the other. The fingerprint covers what the simulator's own check does not, such as a flag or the simulator's version; Verilator's C++ is the compiler cache's to reuse, as no unit of it is a package's. The check still runs before every build, since which files the top needs is what it finds. A fingerprint written last is never that of a build stopped halfway, and the number of jobs changes how fast a build is, not what it builds. A patch is the person's (P28), not a build's. Two members of a workspace may each have a `tb_top`, so each package's builds have a directory of their own. The Make macOS ships, 3.81, compares times in whole seconds, so a source Verilator rewrites in the second the last build's objects were written in looks no newer than them, and the old model is linked; deleting the objects would serve too, but compile the whole model again wherever no compiler cache is installed. |
| B5 | What is built is a top, chosen as P32 chooses one: `--top`, `[package] default-top`, or the only `[top]` table; a root with none and no `--top` is an error. The table's defines are passed as defines, the include directories as include directories, the top as the top module, and its parameters, with `-G`'s after, as Verilator's `-G` | `[top]` already says what a top needs, as a `[[bin]]` does for Cargo. Building every file at its defaults has no top a simulator can start from. |
| B6 | `build` runs `check` on its tops first, and stops at an error. Verilator's lint and style warnings are off, `-Wno-lint -Wno-style`, its other warnings are not fatal, `-Wno-fatal`, but for an elaboration-time `$error` or `$fatal`, `-Werror-USERERROR -Werror-USERFATAL`, and what it writes is shown as it writes it, on stderr | Real designs rarely pass Verilator's lint without waivers, and astli's own checks are the design's: what is left is what this simulator refuses, such as a construct it does not support. An elaboration-time `$error` is how a design refuses parameters it was not written for, and Verilator, which demotes it to a warning, would build it anyway. Verilator reads its file list as one compilation unit, so a macro defined in one file is defined in the next, and a class two files declare is declared twice, which `check` accepts ([P7](packages.md#decisions)); that is the simulator's error, and shown as one. |
| B7 | Verilator builds a testbench written in SystemVerilog, `--binary --timing`, which needs Verilator 5; an older one is refused, naming the version found. A C++ harness and a dependency's DPI sources wait for the manifest to name C and C++ sources | Most PULP testbenches are SystemVerilog alone, and astli knows no other kind of file. A dependency's C++ is the one part of a design that compiles once as Cargo's crates do, and keyed as B3 keys a library it would go to the store too. |
| B8 | A profile is `dev` or `release`, and `dev` is the default; `--release` chooses the other. `[profile.NAME]` sets three knobs, `trace`, `assert` and `threads`, which each backend turns into its own flags, and `[profile.NAME.<simulator>] args` adds flags of its own after astli's. `release` differs from `dev` only in running on four threads. Neither traces; `--trace` on `build` and `run` turns tracing on for one invocation, and `trace = true` for every build of a profile. Only the root's profiles count, a workspace root's in a workspace | Most runs are the short loop of editing a testbench and running it again, on a model small enough that more threads slow it; a regression or a long simulation of a large design asks for `release`, where threads pay most. A waveform is what a debugging session asks for, not that loop: tracing lengthens every compile and slows every simulation, even of a bench that never calls `$dumpvars`, and Verilator's FST links against zlib, whose headers a minimal container or CI image often lacks, so a default that traced would fail a build for a reason the testbench never asked for. No knob asks for optimisation, since none measured changed compile or simulation time (below). Three knobs mean the same in every simulator; what they do not cover is a tool's own and changes with its versions, so it is left to `args`, as D7 keeps the formatter's knobs few. A dependency's profile would change the build of a design that never chose it, as Cargo ignores one too. |
| B9 | `run` builds as `build` does, then runs the result from the current directory (a test runs elsewhere, B12) with the arguments after `--` as they are, and exits with the simulation's status, or where a signal ends it, with 128 and the signal, as a shell does, and a note. `build` and `run` take `-D` and `-I`, but not a filelist's `+define+` and `+incdir+` | A testbench reads its memory images and stimuli by paths relative to where it is run, and passes its options as plusargs. A `$fatal` or a failed assertion then fails a CI job without a script to read the log. Verilator before 5.040 ends a `$fatal` by aborting, having said why, so a signal is no error of astli's. The command line has no `--` the parser keeps a `+define+` from, so it would take a simulation's plusarg for a define; a build reads no filelist, where that spelling comes from. |
| B10 | A test is a module of the package the command acts on marked `(* astli_test *)`, which takes no value; a value, or the attribute on what is no module, is an error at the attribute, reported by `test`. Tests are found in any of the package's files, dev sources included, not a dependency's or a sibling's the package requires by `path`, each file read as written, every branch of a conditional and no macro expanded. A test runs once per point (B15); `--list` writes the points, sorted by test and each test's in the order its sweeps give them, one per line, each after its package's name when the run reads several packages. A filter is a substring of a point's name, or with `--exact` the whole of it, the package's name no part of it, and one matching no point of any package is an error | A testbench saying it is one keeps no list of benches in a script to fall out of step; an attribute is standard syntax other tools ignore. `fmt`'s reading, rather than a build's, because a `[top.NAME]` table's defines may decide whether a module is declared at all, and the table is only chosen once the test is known: reading at the defaults would miss it, or fail on a macro only the table defines. What does not parse is the check's to report, under the defines each test is built with. A filter that matches nothing would pass CI having run nothing. |
| B11 | A test is a top as B5 builds one, under the `[top.NAME]` table of the test's name if there is one, otherwise the module with nothing defined. The tests are checked (B6) once for each set of defines their tables give, all before any is built, and each then adds its file list and fingerprint (B4). Builds and then runs are parallel under `-j`, the builds splitting it evenly among Verilator's own jobs. Every selected test is built and run whatever failed before it, and `--no-run` builds them and runs none | A test needs what a top needs, defines and parameters, so there is no `[test.NAME]`. Most tests have no table and share one check. A failing test in CI should not hide whether the rest pass. Running none lets CI build in one step and run in another. |
| B12 | A run starts in `run/<seed>/` in the point's build directory, emptied first, with `+astli_root=<path>`, the root of the test's package, and `+verilator+seed+N`. The seed is FNV-1a of the point's name, below 2^31 and never 0, unless `--seed` gives one. Standard output and error go to `output.log` there; `astli clean` deletes them with the builds | Parallel tests, seeds, profiles and packages then never overwrite each other's waveforms and logs. This departs from B9: a test is written for `astli test`, so it can take its paths from the plusarg. A seed from the name makes a rerun the same run, and Verilator takes a signed 32-bit seed. |
| B13 | A run passes when the simulation exits with status 0, and fails on any other status, a signal, or running past its `timeout`, after which it is killed. `[test] timeout` bounds every run of the package, in whole seconds, none by default; it is each package's own (P36), and a virtual root's `[test]` is warned of as not read (P38). A run past 60 seconds is reported as still running | `$finish` with no `$error` or `$fatal` is how a SystemVerilog bench says it passed, and Verilator ends a run at its first `$error`, so no `PASS` line is needed. No default timeout fits every design, so only one set kills a run. |
| B14 | A passing run says `Passed` with its time and nothing of its own unless `--nocapture`. A failure is an error saying why, where its log is, and the command that repeats it, `astli test --exact NAME --seed N --trace`, with `-p NAME` when the run read several packages, `--release` if it was given, and `-- ARGS` if they were (B19), followed by the simulation's output on standard output. The run ends with `Finished` and the count, or with the count of tests that failed and their names, and fails. `-p NAME` runs one package's tests, and `--workspace`, or a virtual root without `-p`, every package's under one `-j` and one summary, each test shown after its package's name | The repeat command is what a person runs next, and with waveforms. A simulation's output goes where `run` sends it. Two members may each hold a `tb_top`, so the package's name tells them apart, and it is a flag, `-p`, since it is no part of a test's name. A package's tests are already several designs, so a workspace's are one run rather than one per package, as `check --workspace` makes them. |
| B15 | `(* astli_sweep = "1, 2, 16" *)` on a `parameter` declared in a test's body lists its values, each a number in decimal or an enum member's name, and a bare `(* astli_sweep *)` takes every value of an enum, in the order declared, or of a `bit` or other single bit. The test's points are the product of its swept parameters' values in declaration order, each named for them as `tb_fifo[Depth=16,Mode=Bypass]`, an integral value in decimal and an enum's by its member; a test that sweeps nothing is one point, named as the test. The values are read once the design is elaborated under the test's table (B11), each sweep's in the body the values of those before it give. An error at the attribute: a value the parameter cannot hold, an empty or repeated one, a value that is no string, a type with no short spelling (a real, a string, a struct, an unpacked or a type wider than 64 bits), a bare sweep of a type with more values than an enum or a bit, a `localparam`, a body `parameter` of a module with a `#( ... )` list, which the list makes local (6.20.1), a declaration of several parameters, a test whose table's `params` sets the parameter, and a sweep on a module that is no test. The tests are elaborated even under `--list`, to know their points | Numbers and member names cover the values a bench is swept over, and need no expression evaluated, nor one to keep in step with the code. A bare sweep keeps an enum's list from falling out of step with the type. A parameter's type may depend on one swept before it, so each list is read where those are set. The grammar gives a parameter in a list no attribute, and the parser says so, so a test that sweeps has no list; a body parameter is set by `-G` and a wrapper's override as a list's is. A table setting a swept parameter would undo the sweep. |
| B16 | Each point is a top of its own, its values set as its parameters after its table's, an enum's member going to the simulator's `-G` as its integer, and builds into `<top>/<hash of its values>/` in the package's directory of builds (B4); a test that sweeps nothing builds into `<top>/`. The tests are still checked once for each set of defines their tables give, each point's body elaborated in the check, and only the points selected are checked and built. `-G NAME=VALUE` on `test` sets the parameter in every selected point whose test declares it, and is an error where none does, or on a swept parameter, saying which filter selects that value, `'Depth=16'` | `[`, `=` and `,` in a `--Mdir` are fragile in Verilator's makefile, so the bracket name is for display and selection only. A point adds only what it reaches, its file list and its fingerprint, so one that has not changed is `Fresh`. A flag that sets a parameter only some tests declare is still one flag for the run; one that no test takes is a typo. A filter already selects a swept value. A point is a top, so `--top 'tb_fifo[Depth=16]'` names one in `check`, `lint`, `files`, `elab`, `build` and `run` (P32), and builds into the directory `test` builds it in; `check --tests` and `lint --tests` add every point to what they elaborate. |
| B17 | `--seeds N`, or `[test] seeds = N`, the package's own, runs each point under N random seeds from one build, in place of the seed its name gives; `--seed` takes the place of either, and with `--seeds` is refused. A seed drawn at random is below 2^31, never 0, and different from the point's others, and the run is shown with it, `tb_fifo[Depth=16] seed 1234`, in its status, its failure and the summary. The summary counts runs rather than tests when a point runs more than once | Seeds change only the simulation, so they share a build, as a sweep's values cannot. The run's name says the seed because a seed drawn at random is otherwise nowhere but in the repeat command, and the repeat command's `--seed` must win over the manifest's `seeds` to repeat one run. Each seed already has its directory (B12), so the runs of one test do not collide; they pile up there until `astli clean`. |
| B18 | `--junit PATH` also writes a JUnit report: a `testsuite` for each package with a test selected, and a `testcase` for each run, named by its point and, with random seeds, its seed, its `classname` the package, with its time; a failure is a `failure` whose message says why and whose text is the run's output. A point that did not build is a failure with the build's message; one whose package's check failed is an `error`; under `--no-run` a point built is `skipped`. With no test to run, the report has no suite. `--list` writes none. The XML is written by hand, with `&`, `<`, `>` and quotes escaped and what XML cannot hold replaced | CI test views read JUnit, and grouping by package keeps two members' `tb_top` apart. Every selected point is in the report however it ended, so the view never shows a failure as missing; a check that fails is the package's, not the test's, which `error` says. Writing the report even when nothing ran gives a CI step that uploads it a file to upload. A few elements need no XML library. |
| B19 | `astli test [FILTER] -- ARGS` passes what follows `--` to every selected run's simulation as it is, after `+astli_root` and the seed, as `run` passes them (B9); the command that repeats a failure carries them, each quoted as a shell needs. A run is still a point and a seed: the arguments are the same for every run, and no part of its name or its directory | A bench's own options, such as `+verilator+quiet`, are the same for every run, and `run` already takes them so. What a test needs per run belongs in its source, read from a plusarg with a default or swept as a parameter, so its points stay what a filter selects and the repeat command names. Coming after astli's own, an argument the bench reads twice takes the value given here, where a simulator lets the last win. |

## Profiles

| Knob | `dev` | `release` | Verilator |
| --- | --- | --- | --- |
| `trace` | `false` | `false` | `--trace-fst` |
| `assert` | `true` | `true` | `--no-assert` when `false` |
| `threads` | `1` | `4` | `--threads N` above 1 |

Every Verilator build also gets `--binary --timing -Wno-fatal -Wno-lint
-Wno-style -Werror-USERERROR -Werror-USERFATAL`, `-j` as astli's own, `--top-module`, `--Mdir` and `-f` with the
file list, and from 5.024, which first takes it, `--quiet`. `--trace` sets
`trace` for one build, whatever the profile says. Assertions stay
on in `release`, since they are what a regression checks.

The defaults were measured with Verilator 5.054 on an Apple M1 Pro
of ten cores, on three testbenches of `eda-benchmarks` 0.2.0's simulation
archive, each built and run alone, in seconds:

| Flags over Verilator's own | cv32e40p `hello_world` | ita `S128…Gelu` | pulp_c910 `coremark` |
| --- | --- | --- | --- |
| none | 3.6 build, 0.1 run | 4.7, 3.3 | 31.0, 31.1 |
| `-O3` | 3.3, 0.1 | 4.6, 3.4 | 30.9, 31.3 |
| C++ `-O2` for `OPT_FAST` and `OPT_GLOBAL` | 3.8, 0.2 | 5.0, 3.3 | 30.1, 30.5 |
| `-O3`, C++ `-O3` | 3.8, 0.2 | 4.4, 3.4 | 30.5, 29.2 |
| `-O3`, C++ `-O2`, `--threads 2` | | 4.5, 3.5 | 34.4, 19.5 |
| `-O3`, C++ `-O2`, `--threads 4` | | 4.0, 3.6 | 34.0, 11.5 |

Optimisation moved nothing beyond a few percent, while four threads ran the
large model 2.7 times as fast for a tenth more compile time and slowed the
small one by a tenth.

## Prior art

Cargo gives the commands, the profiles and the fingerprinted build directory,
and its metadata hash is B3's key. Questa's `vlib`/`vlog -work`, VCS's
`vlogan` with its setup file's library map, Xcelium's `xrun -makelib` and xsim's
`xvlog -work` are the separate compilation B2 relies on. FuseSoC drives
simulators through Edalize, a backend per tool writing that tool's script
into `build/`; bender's `script` writes a script per tool and leaves running
it to the flow, which is what [P29](packages.md#decisions) chose before
`build`.
